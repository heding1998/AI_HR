# Spec 0001：简历初筛 MVP（AI 简历评分链路）

## Problem Statement

HR 在招聘旺季每天面对大量简历（人均每月约 200~1500+ 份），人工逐份初筛耗时巨大、人力成本高、筛选质量不稳定。公司希望用 AI 把「简历初筛」自动化：HR 只需上传简历压缩包，系统自动完成 PDF 解析、简历内容提取、AI 评分，并沉淀高分人才库与应聘列表，从而把 HR 从机械的初筛工作中解放出来。

## Solution

构建一套内部使用的 AI 简历初筛系统（MVP）。HR 登录后维护招聘岗位与评分标准，上传某岗位的简历 ZIP 包；系统异步解压、解析 PDF、提取结构化简历内容、按评分标准打分（0~10 分），生成应聘记录，并将达标候选人自动纳入高分人才库（按人去重）。前端提供登录、岗位管理、评分标准配置、简历上传、评分结果、高分人才库共 6 类页面。

## User Stories

1. 作为 HR，我想用账号登录系统，以便安全地使用平台功能。
2. 作为管理员，我想有一个预置的默认管理员账号，以便首次登录系统。
3. 作为 HR，我想查看招聘岗位列表，以便了解当前在招岗位。
4. 作为 HR，我想新建一个招聘岗位，以便为该岗位的简历评分建立前提。
5. 作为 HR，我想编辑或停用一个岗位，以便维护岗位信息。
6. 作为 HR，我想为某岗位配置评分标准 A 表（大类/小类及其分数），以便定义评分维度与分值。
7. 作为 HR，我想为某岗位配置评分标准 B 表（大类/小类/一级指标/二级指标/权重），以便定义具体评分规则。
8. 作为 HR，我想在配置评分标准时看到保存结果与校验提示，以便及时发现配置错误。
9. 作为 HR，我想查看某岗位是否已配置评分标准，以便上传简历前确认就绪。
10. 作为 HR，我想把包含多份 PDF 简历的 ZIP 文件上传到某岗位，以便批量初筛。
11. 作为 HR，我想在上传后看到处理进度，以便知道何时完成。
12. 作为系统，我想解压 ZIP 并逐份提取 PDF 文本，以便后续结构化处理。
13. 作为系统，我想把原始简历文件存入对象存储，以便留存与追溯。
14. 作为系统，我想从简历文本中提取 13 个结构化字段（姓名/性别/年龄/最高学历/联系方式/工作年限/求职意向/期望薪资/期望城市/个人技能/工作经验/项目经验/自我评价），以便统一存储与评分。
15. 作为系统，我想在简历内容提取失败时将该简历标记为异常并记录原因，以便 HR 定位问题。
16. 作为系统，我想依据岗位评分标准对每份简历评分（0~10 分），以便量化岗位匹配度。
17. 作为系统，我想在评分失败时记录失败状态并支持重试，以便不丢失数据。
18. 作为系统，我想把评分结果写入应聘记录并设置初筛状态，以便 HR 查看。
19. 作为 HR，我想按岗位查看评分结果列表并按分数排序，以便快速定位高分简历。
20. 作为 HR，我想查看某份简历的提取详情与原文，以便人工复核。
21. 作为系统，我想把评分 ≥ 7 的候选人自动加入高分人才库，以便沉淀高质量人才。
22. 作为系统，我想按「姓名 + 手机号」对人才库去重，以便避免同一候选人重复入库。
23. 作为系统，我想在人才库中保留候选人的最高分与分级，以便排序与筛选。
24. 作为 HR，我想查看高分人才库并按分级（一般/中等/特别优秀）筛选，以便跨岗位复用人才。
25. 作为 HR，我想删除或忽略某份异常简历，以便清理无效数据。
26. 作为 HR，我想在操作失败时看到明确的错误提示，以便知道问题出在哪里。

## Implementation Decisions

- **技术栈**：后端 Python + FastAPI；前端 Vue3 + Element Plus（Vite）；异步任务 Celery + Redis；数据库 PostgreSQL（含 pgvector 扩展，本期暂不用于检索）；对象存储 MinIO（S3 兼容）。
- **领域模型**：沿用 `CONTEXT.md` 术语——候选人(Candidate)、简历(Resume)、简历内容(Resume Content)、招聘岗位(Job)、评分标准(Scoring Standard)、简历评分(Resume Score)、应聘记录(Application)、高分人才库(Talent Pool)。
- **评分分制**：全系统 0~10 分制（见 `docs/adr/0001-resume-score-scale-0-to-10.md`）。
- **评分公式**（来自 SOP 文档）：`小类得分 = 匹配权重 / 最高权重(10) × 小类分数`；`大类得分 = 该类下小类得分之和`；`总分 = 各大类得分之和`。未匹配到的小类得分为 0。
- **LLM 接入**：抽象一层 LLM 适配器，本期实现 DeepSeek（`deepseek-chat`）。API Key 通过环境变量注入（`DEEPSEEK_API_KEY`），未配置时 AI 环节不可用但其余流程不受影响。
- **简历格式**：MVP 仅支持 PDF；解析用 pdfplumber 提取文本。
- **异步处理**：以「上传批次(upload_batch)」为任务单元，Celery 后台解析+提取+评分，前端轮询批次进度。
- **去重规则**：候选人按「姓名 + 手机号」唯一；高分人才库内同一候选人仅一条记录，取最高分。
- **数据模型（核心表）**：
  - users：登录账号（含默认管理员）。
  - jobs：招聘岗位。
  - scoring_standard_a：A 表（岗位、大类、小类、大类分数、小类分数）。
  - scoring_standard_b：B 表（岗位、大类、小类、一级指标、二级指标、权重）。
  - candidates：候选人（姓名、手机号、`profile` JSONB 承载 13 字段；`UNIQUE(name, phone)`）。
  - resumes：简历（MinIO 文件键、原始文件名、`extracted_content` JSONB）。
  - applications：应聘记录（岗位、候选人、简历、分数、状态枚举、时间）。
  - talent_pool：高分人才库（候选人、来源岗位、最高分、分级枚举；`UNIQUE(candidate_id)`）。
  - upload_batches：上传批次（岗位、总文件数、已处理数、状态）。
- **应聘状态枚举**：沿用 SOP 全量状态（创建/初筛通过/初筛不通过/复筛…/录取），MVP 仅使用「创建、初筛通过、初筛不通过」。
- **人才库分级阈值**：`[7, 8)` 一般优秀、`[8, 9)` 中等优秀、`≥ 9` 特别优秀。

## Testing Decisions

- **测试原则**：只测外部可观察行为，不测实现细节；对 LLM 与对象存储等外部依赖一律替换为 fake/mock，保证测试离线可跑、快速稳定。
- **主要测试接缝（seams）**：
  1. LLM 适配层接口（文本进、结构化 JSON 出）——以 fake 实现替换 DeepSeek；
  2. 对象存储客户端接口——以内存或本地 fake 替换 MinIO；
  3. 评分计算纯函数（A/B 表 + 匹配权重 → 分数）——纯逻辑，直接单测；
  4. 候选人去重与人才库分级逻辑——纯逻辑，直接单测；
  5. HTTP API 层——集成测试（登录、岗位/评分标准 CRUD、上传、结果查询、人才库查询）。
- **被测模块**：PDF 文本提取、简历内容提取（输出 JSON 校验）、评分计算、去重/分级、批次进度、各 API 端点。
- **先例**：项目目前无既有测试，本 Spec 的测试从零建立。

## Out of Scope

招聘计划、HR 人工复筛、多轮面试、AI 数字人面试官、面试官知识库/培训、笔试、面相分析、报表统计、自我学习、AI 可观测性统计、图片简历/OCR、多租户、真实对象存储上云、pgvector 向量检索的实际使用。

## Further Notes

- DeepSeek API Key 以环境变量占位；在提供 Key 之前，脚手架、数据模型、上传解析等步骤可先行开发与联调。
- pgvector 扩展本期随数据库一并部署，但不承载任何检索功能，为后续面试官知识库/笔试题库的 RAG 预留。
- 评分标准本期以「示例岗位 + 示例评分标准」作为种子数据，且提供配置界面供 HR 自行维护。
